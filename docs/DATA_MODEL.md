# NEXUS AI — Database Data Model

**Status:** Phase 1 — Planning  
**Database:** Cloudflare D1 (SQLite)  
**Architecture:** Multi-tenant, relational, server-enforced access control  
**Scope:** R1, R1.1, R2 and R3+

This document defines the planned database structure. Nothing is implemented until the corresponding development phase is completed and tested.

Related documents:
- `docs/ARCHITECTURE.md`
- `docs/PRODUCT_REQUIREMENTS.md`

---

## 1. Database Principles

1. Cloudflare D1 compatible SQLite schema.
2. Every business-data record belongs to a workspace.
3. Workspace access is verified by the backend, never trusted from client input.
4. Foreign keys are enabled and enforced.
5. All primary keys use UUID strings.
6. All timestamps are stored in UTC as ISO 8601 strings.
7. Money is stored as integer minor units with an ISO 4217 currency code.
8. Floating-point values are never used for financial amounts.
9. Passwords are stored as strong salted hashes, never plaintext.
10. Secrets and integration tokens are encrypted before storage.
11. Database access must go through a centralized workspace-aware data-access layer.
12. Schema changes use versioned migrations.
13. Indexes must support workspace-scoped queries.
14. Destructive operations must follow retention and audit policies.

## 2. Naming and Common Conventions

- Table names: lowercase snake_case, plural.
- Column names: lowercase snake_case.
- Primary key: `id TEXT PRIMARY KEY`.
- Workspace reference: `workspace_id TEXT NOT NULL`.
- Creation timestamp: `created_at TEXT NOT NULL`.
- Update timestamp: `updated_at TEXT NOT NULL`.
- Boolean values: SQLite INTEGER (`0` or `1`).
- Currency: three-character ISO 4217 code.
- IDs are generated by the application using UUIDs.
- Foreign keys use explicit `ON DELETE` behavior.

The backend must generate timestamps and IDs. Client-supplied workspace IDs must never determine authorization.

## 12. Workspace Isolation Requirements

Every workspace-owned table must have a `workspace_id`.

Examples:
- customers
- businesses
- financial_transactions
- students
- attendance_records
- ai_proposals
- telegram_messages
- knowledge_notes

Mandatory rules:

1. The backend derives the workspace from verified membership.
2. Every query filters by the authorized workspace.
3. Related records must be verified to belong to the same workspace.
4. Foreign keys alone do not guarantee workspace isolation.
5. Cross-workspace access tests are required for every endpoint.
6. Workspace IDs received from clients are never authorization evidence.
7. Composite unique constraints and foreign keys should be used where needed to prevent cross-workspace relationships.
8. R2 files, if introduced, use workspace-specific prefixes and server-side authorization.

- `attendance_records(workspace_id, attendance_date)`
- `student_fee_records(workspace_id, payment_status)`
- `ai_usage(workspace_id, usage_date)`
- `ai_proposals(workspace_id, status, expires_at)`
- `telegram_conversations(workspace_id, connection_id)`
- `telegram_messages(workspace_id, conversation_id, created_at)`
- `notifications(workspace_id, user_id, read_at)`
- `audit_logs(workspace_id, created_at)`

Indexes must be validated using actual query patterns and SQLite query plans.

## 14. Data Retention and Deletion

1. Account deletion follows the approved privacy and retention policy.
2. Workspace deletion must not bypass legal retention requirements.
3. Financial records may require retention under applicable law.
4. Integration disconnection removes stored credentials and unregisters webhooks.
5. Personal information is minimized and protected.
6. Audit records follow a defined retention policy.
7. Backups follow the same security and Zero-Cost requirements.
8. Deletion operations must be tested and audited.

## 15. Database Migration Strategy

- Every schema change is a numbered SQL migration.
- Migrations are stored in the repository under `database/migrations/`.
- Migrations are applied in order.
- Each migration is reviewed and tested before deployment.
- Destructive schema changes require explicit review.
- Development and production migration state must be tracked.
- Rollback or recovery procedures are documented for risky changes.

## 16. Implementation Requirements

Before production use:

- Add actual SQLite DDL migrations for each implemented phase.
- Enable and verify foreign-key enforcement.
- Add workspace isolation tests.
- Add permission tests for all sensitive operations.
- Add validation for money, dates, statuses and IDs.
- Test duplicate Telegram webhook delivery.
- Test token encryption and secret handling.
- Test migration behavior on a clean database and an existing database.
- Verify indexes with representative queries.
- Confirm all schema decisions against the latest Architecture and Product Requirements.

This document is a planning specification, not evidence of implemented or tested database functionality.
